# Static area data — provenance & validation status

`<patch>/areas.json` is generated by `node scripts/gen-areas.mjs` from the curated
table inside that script. Regenerate with `npm run gen:areas` and commit both files.

## Provenance

The acts 1–10 zone lists (names, act membership, canonical progression order,
town/waypoint/side flags, approximate monster levels) are **hand-curated** from
community-documented campaign structure (poewiki area pages, poedb, and the zone
lists used by speedrun autosplitters). The campaign layout has been stable since
3.0; monster levels are approximate (±2) and only used to disambiguate duplicate
zone names between Acts 1–5 and 6–10, whose levels differ by 30+.

Automated exports (RePoE `world_areas.json`, poe-log-monitor `areas.json`,
poewiki Cargo API) were unreachable from the build sandbox; if you can reach
them, prefer regenerating this table from one of those and note it here.

## What the tracker does and does not rely on

- **Relied on:** display `name` (exactly as `You have entered <name>.` prints it),
  `act`, `order`, `kind`/`town`, and coarse `level` for duplicate-name resolution.
- **Not relied on:** the game's internal area ids (`1_1_2`-style from
  `Generating level N area "..."` lines). This file's `id` values are synthetic
  slugs (`a6-the-coast`), not client ids. The tracker records the **observed**
  client id of every segment (`zone_segments.client_area_id`) and only uses the
  `<part>_<act>_<n>` prefix pattern as an act *hint* — so wrong or missing id
  knowledge can never misattribute a zone.

## Validation

- `cargo test -p leaguestart-core` asserts: unique ids, duplicate display names
  resolve to exactly one area per act, per-act zone counts, and that every area
  referenced by the test fixtures resolves.
- **Real-log validation (open):** after playing with the app once, compare the
  collected `client_area_id` values against this table (names that resolved to
  `unknown` or levels far from the observed `Generating` level indicate a curation
  error) and fix the table. This is the post-MVP validation step from the project
  plan.
